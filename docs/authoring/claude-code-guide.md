# Claude Code 활용 가이드

이 문서는 Anthropic의 [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)를 한국어로 정리한 것입니다. 스킬 하나를 잘 쓰는 법이 아니라 **Claude Code라는 도구 자체를 잘 쓰는 법** — 환경 설정, 프롬프트 쓰는 법, 세션 관리, 자동화 — 을 다룹니다. 스킬 파일 작성법은 [스킬 작성 가이드](./skill-authoring-guide.md)가 마스터이고, 같은 층위의 OpenAI Codex 문서는 [Codex 활용 가이드](./codex-guide.md)에 정리해 두었습니다.

---

## 전제: 컨텍스트 윈도우가 모든 것을 결정한다

대부분의 모범 사례는 **제약 하나**에서 나옵니다 — Claude의 컨텍스트 윈도우는 빠르게 차고, **차오를수록 성능이 떨어진다.**

컨텍스트 윈도우에는 대화 전체가 들어갑니다: 모든 메시지, Claude가 읽은 모든 파일, 실행한 모든 명령의 출력까지. 디버깅 한 번, 코드베이스 탐색 한 번이 수만 토큰을 씁니다. 컨텍스트가 차면 Claude는 앞서 받은 지시를 "잊기" 시작하고 실수가 늘어납니다.

**컨텍스트는 이 도구에서 가장 중요한 자원입니다.** 아래 규칙 대부분은 결국 "이 자원을 어떻게 아끼는가"의 변주입니다.

## 1. 검증 수단을 쥐여 준다

> **Claude가 스스로 돌릴 수 있는 검사를 준다 — 테스트, 빌드, 비교할 스크린샷. 지켜봐야 하는 세션과 자리를 비워도 되는 세션의 차이가 여기서 갈립니다.**

Claude는 **일이 끝나 보이면** 멈춥니다. 스스로 돌릴 검사가 없으면 "끝나 보인다"가 유일한 신호이고, **사람이 검증 루프가 됩니다** — 모든 실수가 사람이 알아챌 때까지 방치됩니다. 통과/실패가 나오는 무언가를 쥐여 주면 루프가 스스로 닫힙니다: 작업 → 검사 실행 → 결과 읽기 → 통과할 때까지 반복.

검사는 대화 안에서 **읽을 수 있는 신호**를 내는 것이면 무엇이든 됩니다 — 테스트 스위트, 빌드 종료 코드, 린터, 산출물을 기준 파일과 비교하는 스크립트, 디자인과 대조할 브라우저 스크린샷.

| 전략 | 이렇게 말고 | 이렇게 |
| --- | --- | --- |
| **검증 기준을 함께 준다** | "이메일 주소를 검증하는 함수를 만들어줘" | "validateEmail 함수를 써줘. 예시 케이스: `user@example.com`은 true, `invalid`는 false, `user@.com`은 false. 구현 후 테스트를 실행해줘" |
| **UI 변경은 눈으로 검증** | "대시보드를 더 낫게 만들어줘" | "[스크린샷 첨부] 이 디자인대로 구현하고, 결과를 스크린샷으로 찍어 원본과 비교해줘. 차이를 나열하고 고쳐줘" |
| **증상이 아니라 원인** | "빌드가 실패해" | "빌드가 이 에러로 실패해: [에러 붙여넣기]. 고치고 빌드 성공을 확인해줘. 에러를 억누르지 말고 근본 원인을 잡아줘" |

검사를 만들었다면, 그것이 **멈춤을 얼마나 강하게 막는지**를 정합니다.

- **한 프롬프트 안에서** — 위 표처럼 "검사를 돌리고 통과할 때까지 반복해줘"라고 같은 메시지에 적는다
- **세션 전체에 걸쳐** — `/goal` 조건으로 걸면 매 턴 후 별도 평가자가 다시 확인하고, 조건이 풀릴 때까지 계속 작업한다
- **결정적 게이트로** — Stop 훅이 검사를 스크립트로 돌려 통과 전까지 턴 종료를 막는다(연속 8회 차단되면 Claude Code가 훅을 넘기고 턴을 끝낸다)
- **제3자 검토로** — 검증용 서브에이전트가 새 컨텍스트에서 결과를 반박해 본다. **작업한 쪽이 채점까지 하지 않게** 하는 장치다

각 방법은 **설정 비용과 주의력을 맞바꿉니다.** 프롬프트 방식은 오늘 당장 아무 작업에나 쓸 수 있고, `/goal`·Stop 훅은 **지켜보지 않는 실행이 제대로 끝나게** 해줍니다.

성공했다는 주장 대신 **증거를 내놓게** 하세요 — 테스트 출력, 실행한 명령과 그 반환값, 결과 스크린샷. 증거를 읽는 편이 검증을 직접 다시 돌리는 것보다 빠르고, 지켜보지 않은 세션에도 통합니다.

## 2. 탐색 → 계획 → 구현 순서로 간다

> **조사·계획을 구현과 분리해야 엉뚱한 문제를 푸는 일을 막습니다.**

바로 코딩에 들어가게 두면 **틀린 문제를 푸는 코드**가 나올 수 있습니다. 플랜 모드로 탐색과 실행을 분리합니다.

1. **탐색** — `Shift+Tab`을 눌러 `⏸ plan mode on`이 될 때까지 전환하거나 `claude --permission-mode plan`으로 시작합니다. Claude가 파일을 읽고 질문에 답하되 **아무것도 바꾸지 않습니다.**
   `/src/auth를 읽고 세션·로그인 처리 방식을 파악해줘. 비밀값을 환경변수로 어떻게 관리하는지도 봐줘.`
2. **계획** — 상세 구현 계획을 요청합니다. `Ctrl+G`로 계획을 에디터에서 직접 고칠 수 있습니다.
   `Google OAuth를 추가하려고 해. 어떤 파일이 바뀌어야 해? 세션 흐름은? 계획을 만들어줘.`
3. **구현** — 계획을 승인하거나 `Shift+Tab`으로 모드를 빠져나온 뒤, 계획과 대조하며 작성하게 합니다.
   `네 계획대로 OAuth 흐름을 구현해줘. 콜백 핸들러 테스트를 쓰고, 테스트를 돌려 실패를 고쳐줘.`
4. **커밋** — `설명이 담긴 메시지로 커밋하고 PR을 열어줘.`

**다만 플랜 모드에는 비용이 있습니다.** 오타 수정, 로그 한 줄 추가, 변수 이름 변경처럼 범위가 명확하고 작은 일은 그냥 시키세요. 계획이 값을 하는 건 **접근 방식이 불확실할 때, 여러 파일이 바뀔 때, 건드릴 코드가 낯설 때**입니다. **diff를 한 문장으로 설명할 수 있으면 계획은 건너뜁니다.**

## 3. 프롬프트에 구체적인 맥락을 준다

> **지시가 정확할수록 나중에 고쳐줄 일이 줄어듭니다.**

Claude는 의도를 추론할 수 있지만 마음을 읽지는 못합니다. 파일을 구체적으로 지목하고, 제약을 말하고, 따라야 할 기존 패턴을 가리키세요.

| 전략 | 이렇게 말고 | 이렇게 |
| --- | --- | --- |
| **범위를 좁힌다** — 어느 파일, 어떤 시나리오, 테스트 취향까지 | "foo.py에 테스트 추가해줘" | "foo.py에서 **로그아웃 상태** 엣지 케이스를 다루는 테스트를 써줘. 목(mock)은 쓰지 마." |
| **출처를 가리킨다** — 답이 있는 곳을 지목 | "ExecutionFactory API는 왜 이렇게 이상해?" | "ExecutionFactory의 git 히스토리를 훑어서 이 API가 어떻게 지금 모양이 됐는지 요약해줘" |
| **기존 패턴을 참조시킨다** | "캘린더 위젯 추가해줘" | "홈 화면의 기존 위젯 구현을 보고 패턴을 파악해줘 — HotDogWidget.php가 좋은 예야. 그 패턴을 따라 월 선택과 연도 페이지네이션이 되는 캘린더 위젯을 만들어줘. 이미 쓰는 라이브러리 외에 새로 추가하지 말고." |
| **증상을 설명한다** — 증상 + 짐작되는 위치 + "고쳐진 상태"의 정의 | "로그인 버그 고쳐줘" | "세션 타임아웃 후 로그인이 실패한다는 제보가 있어. src/auth/의 인증 흐름, 특히 토큰 갱신을 확인해줘. 재현하는 실패 테스트를 먼저 쓰고 그다음 고쳐줘" |

**모호한 프롬프트가 쓸모 있을 때도 있습니다** — 탐색 단계라 방향을 되잡을 여유가 있을 때입니다. "이 파일에서 뭘 개선하겠어?" 같은 질문은 내가 물어볼 생각조차 못 한 것을 끄집어냅니다.

### 풍부한 입력을 준다

- **`@`로 파일 참조** — 코드가 어디 있는지 설명하는 대신 지목하면 Claude가 먼저 읽고 답합니다
- **이미지는 그대로 붙여넣기** — 복사/붙여넣기 또는 드래그 앤 드롭
- **문서·API 레퍼런스는 URL로** — 자주 쓰는 도메인은 `/permissions`로 허용 목록에 올려 둡니다
- **데이터는 파이프로** — `cat error.log | claude`
- **필요한 걸 직접 가져오게** — Bash 명령·MCP 도구·파일 읽기로 스스로 맥락을 끌어오라고 시킵니다

## 4. 환경을 설정한다

몇 가지 초기 설정만으로 이후 모든 세션의 성능이 달라집니다.

### CLAUDE.md를 잘 쓴다

> `/init`으로 현재 프로젝트 구조에 맞는 초안을 만든 뒤 다듬어 나가세요.

`CLAUDE.md`는 **모든 대화 시작 시 Claude가 읽는 파일**입니다. Bash 명령, 코드 스타일, 워크플로 규칙 — 코드만 봐서는 알 수 없는 지속적 맥락을 담습니다. 정해진 형식은 없고, **짧고 사람이 읽기 좋게** 두는 것이 핵심입니다.

```markdown
# Code style
- Use ES modules (import/export) syntax, not CommonJS (require)
- Destructure imports when possible (eg. import { foo } from 'bar')

# Workflow
- Be sure to typecheck when you're done making a series of code changes
- Prefer running single tests, and not the whole test suite, for performance
```

`/context`로 파일이 실제로 로드됐는지 확인합니다. **매 세션 로드되므로 넓게 적용되는 것만** 넣고, 가끔만 필요한 도메인 지식·워크플로는 **스킬로 내립니다** — 스킬은 필요할 때만 로드돼 모든 대화를 무겁게 만들지 않습니다.

한 줄마다 물어보세요: **"이 줄을 지우면 Claude가 실수하게 되나?"** 아니면 지웁니다. **비대해진 CLAUDE.md는 정작 지켜야 할 지시를 묻히게 만듭니다.**

| ✅ 넣을 것 | ❌ 빼야 할 것 |
| --- | --- |
| Claude가 짐작할 수 없는 Bash 명령 | 코드를 읽으면 알 수 있는 것 |
| 기본값과 다른 코드 스타일 규칙 | Claude가 이미 아는 표준 언어 관례 |
| 테스트 방법·선호하는 테스트 러너 | 상세 API 문서 (링크로 대체) |
| 저장소 예절 (브랜치 명명, PR 관례) | 자주 바뀌는 정보 |
| 이 프로젝트만의 아키텍처 결정 | 긴 설명이나 튜토리얼 |
| 개발 환경의 특이사항 (필수 환경변수) | 파일별 코드베이스 설명 |
| 흔한 함정·직관에 어긋나는 동작 | "깨끗한 코드를 써라" 같은 자명한 말 |

**규칙이 있는데도 Claude가 계속 어긴다면 파일이 너무 길어 그 규칙이 묻힌 것입니다.** CLAUDE.md에 답이 있는 걸 Claude가 되묻는다면 문장이 모호한 것입니다. **CLAUDE.md를 코드처럼 다루세요** — 문제가 생기면 검토하고, 주기적으로 쳐내고, 고친 뒤 실제로 행동이 바뀌는지 관찰합니다.

특정 지시를 계속 건너뛴다면 **그 줄에만** "IMPORTANT" 같은 강조를 답니다 — 여러 줄을 강조하면 아무것도 두드러지지 않습니다.

### 권한을 설정한다

승인 프롬프트를 줄이되 통제를 잃지 않는 방법입니다.

- **권한 허용 목록** — `npm run lint`, `git commit`처럼 안전하다고 아는 도구를 미리 승인 (`/permissions`)
- **샌드박싱** — OS 수준 격리로 파일시스템·네트워크 접근을 제한하고, 그 경계 안에서는 자유롭게 (`/sandbox`)

Pro·Max·Team 플랜의 대화형 세션은 **auto 모드**가 기본입니다 — 별도 분류 모델이 대부분의 행동을 대신 검토하고, 범위 이탈·미확인 인프라·악의적 콘텐츠에 유도된 행동처럼 위험해 보이는 것만 막습니다. 그 외 플랜의 기본인 **Manual 모드**는 파일 쓰기·Bash·MCP 도구를 매번 묻는데, 안전하지만 열 번째 승인쯤에는 검토가 아니라 클릭이 됩니다.

### CLI 도구를 쓰게 한다

외부 서비스와 상호작용할 땐 `gh`·`aws`·`gcloud`·`sentry-cli` 같은 **CLI 도구가 컨텍스트 면에서 가장 효율적**입니다. GitHub를 쓴다면 `gh` CLI를 설치하세요 — 이슈 생성·PR 열기·코멘트 읽기를 Claude가 이미 압니다. 없으면 API를 직접 쓰는데, 인증 없는 요청은 곧 레이트 리밋에 걸립니다.

모르는 CLI도 잘 배웁니다: `foo-cli-tool --help로 사용법을 익힌 다음 A, B, C를 해줘.`

### MCP 서버를 연결한다

`claude mcp add`로 이슈 트래커·데이터베이스·모니터링·Figma 등을 붙이면 그 데이터를 직접 다루게 할 수 있습니다.

### 훅을 건다

**예외 없이 매번 일어나야 하는 일**에는 훅을 씁니다. CLAUDE.md의 지시는 권고지만 **훅은 결정적**이라 실행을 보장합니다. Claude에게 훅을 써 달라고 해도 됩니다: `파일 편집마다 eslint를 돌리는 훅을 써줘` / `migrations 폴더 쓰기를 막는 훅을 써줘`.

### 스킬을 만든다

`.claude/skills/` 아래 `SKILL.md`를 두면 프로젝트·팀·도메인 고유 지식과 반복 워크플로를 Claude가 **필요할 때 자동으로** 적용하거나, `/스킬이름`으로 직접 부를 수 있습니다. 부작용이 있어 수동으로만 부르고 싶은 워크플로는 frontmatter에 `disable-model-invocation: true`를 답니다. 작성법은 [스킬 작성 가이드](./skill-authoring-guide.md) 참고.

### 서브에이전트를 정의한다

`.claude/agents/`에 **자기 컨텍스트와 자기 도구 목록을 가진** 전문 에이전트를 정의합니다. 파일을 많이 읽거나 특정 관점에 집중해야 하는 작업을 메인 대화를 어지럽히지 않고 맡길 때 유용합니다.

```markdown
---
name: security-reviewer
description: Reviews code for security vulnerabilities
tools: Read, Grep, Glob, Bash
model: opus
---
You are a senior security engineer. Review code for:
- Injection vulnerabilities (SQL, XSS, command injection)
- Authentication and authorization flaws
- Secrets or credentials in code
- Insecure data handling

Provide specific line references and suggested fixes.
```

쓸 때는 명시적으로 말합니다: `서브에이전트로 이 코드의 보안 이슈를 검토해줘.`

### 플러그인을 설치한다

`/plugin`으로 마켓플레이스를 둘러봅니다. 플러그인은 스킬·훅·서브에이전트·MCP 서버를 **설정 없이 설치되는 한 덩어리**로 묶은 것입니다.

## 5. 효과적으로 대화한다

### 코드베이스에 질문한다

다른 엔지니어에게 물을 법한 것을 그대로 물으면 됩니다 — 특별한 프롬프트 기술이 필요 없습니다.

- 로깅은 어떻게 동작해?
- 새 API 엔드포인트는 어떻게 만들어?
- `foo.rs` 134행의 `async move { ... }`는 뭘 하는 거야?
- `CustomerOnboardingFlowImpl`은 어떤 엣지 케이스를 다뤄?
- 333행에서 왜 `bar()`가 아니라 `foo()`를 호출해?

낯선 코드베이스에 적응할 때 특히 효과적이고, 다른 엔지니어의 부담도 줄여 줍니다.

### 나를 인터뷰하게 시킨다

큰 기능은 **Claude가 먼저 나를 인터뷰하게** 합니다. 내가 아직 생각하지 못한 것 — 기술적 구현, UI/UX, 엣지 케이스, 트레이드오프 — 을 물어옵니다.

```text
[한 줄 설명]을 만들고 싶어. AskUserQuestion 도구로 나를 상세히 인터뷰해줘.

기술 구현, UI/UX, 엣지 케이스, 우려사항, 트레이드오프를 물어봐. 뻔한 질문 말고,
내가 미처 생각 못 했을 어려운 지점을 파고들어줘.

다 다룰 때까지 계속 묻고, 끝나면 완전한 명세를 SPEC.md에 써줘.
```

명세가 끝나면 **새 세션에서 실행합니다** — 깨끗한 컨텍스트가 온전히 구현에만 쓰이고, 참조할 문서가 손에 남습니다. 좋은 명세는 **자기완결적**입니다: 관련 파일과 인터페이스를 이름으로 지목하고, **범위 밖이 무엇인지** 밝히고, **기능이 동작함을 증명하는 종단 검증 단계**로 끝납니다. 명세를 정밀하게 만드는 데 쓴 시간이 구현을 지켜보는 시간보다 남는 게 많습니다.

## 6. 세션을 관리한다

대화는 저장되고 되돌릴 수 있습니다. 이 점을 적극적으로 활용하세요.

### 빨리, 자주 되잡는다

- **`Esc`** — 작업 도중 멈춥니다. 컨텍스트는 보존되므로 방향만 바꾸면 됩니다
- **`Esc + Esc` 또는 `/rewind`** — 되감기 메뉴를 열어 이전 대화·코드 상태로 복원하거나 특정 메시지부터 요약합니다
- **"방금 것 되돌려"** — 변경을 되돌리게 합니다
- **`/clear`** — 관련 없는 작업 사이에 컨텍스트를 초기화합니다

**같은 문제로 두 번 넘게 고쳐줬다면 컨텍스트가 실패한 접근들로 오염된 상태입니다.** `/clear`하고, 그동안 배운 것을 반영한 **더 구체적인 프롬프트로 새로 시작**하세요 — 누적된 수정이 쌓인 긴 세션보다 거의 항상 낫습니다.

### 컨텍스트를 적극적으로 관리한다

- 관련 없는 작업 사이엔 **자주 `/clear`**
- 자동 압축(compaction)이 걸리면 코드 패턴·파일 상태·핵심 결정 위주로 요약됩니다
- 더 통제하고 싶으면 `/compact <지시>` — 예: `/compact API 변경 위주로`
- 대화의 **일부만** 압축하려면 `Esc + Esc`(또는 `/rewind`)에서 체크포인트를 고르고 **"여기부터 요약" / "여기까지 요약"**을 씁니다
- 압축 동작을 CLAUDE.md에서 지정할 수 있습니다 — `"압축할 때 수정된 파일 전체 목록과 테스트 명령은 항상 보존할 것"`
- 컨텍스트에 남길 필요 없는 곁가지 질문은 `/btw` — 답이 대화 기록에 들어가지 않습니다

### 조사는 서브에이전트에게 시킨다

컨텍스트가 근본 제약이므로, **조사 과정을 메인 대화 밖에 둡니다.** 코드베이스를 조사하면 파일을 잔뜩 읽고 그게 전부 내 컨텍스트를 먹지만, 서브에이전트는 **별도 컨텍스트에서 읽고 요약만 보고**합니다.

```text
서브에이전트로 우리 인증 시스템이 토큰 갱신을 어떻게 처리하는지,
재사용할 만한 기존 OAuth 유틸리티가 있는지 조사해줘.
```

### 체크포인트로 되감는다

보낸 프롬프트마다 체크포인트가 생기고, Claude는 변경 전 파일을 스냅샷해 둡니다. 대화만, 코드만, 또는 둘 다 복원할 수 있습니다. 덕분에 **모든 수를 신중히 계획하는 대신 과감한 시도를 시켜 보고, 아니면 되감는** 방식이 가능합니다.

⚠️ 체크포인트는 **Claude의 파일 편집 도구를 거친 변경만** 추적합니다. Bash 명령이나 외부 프로세스가 만든 변경은 잡히지 않습니다 — **git을 대체하지 않습니다.**

### 대화를 이어서 한다

`claude --continue`로 직전 세션을 잇고, `claude --resume`으로 목록에서 고릅니다. `/rename`으로 `oauth-migration`처럼 이름을 붙여 **작업 흐름별 브랜치처럼** 다루면 나중에 찾기 쉽습니다.

## 7. 자동화하고 확장한다

### 비대화형 모드

`claude -p "프롬프트"`로 CI 파이프라인·pre-commit 훅·스크립트에 넣습니다.

```bash
# 단발 질의
claude -p "Explain what this project does"

# 스크립트용 구조화 출력
claude -p "List all API endpoints" --output-format json

# 실시간 처리용 스트리밍
claude -p "Analyze this log file" --output-format stream-json --verbose
```

`json`은 `result` 필드를 가진 객체 하나를, `stream-json`은 줄마다 JSON 객체 하나를 냅니다.

### 여러 세션을 동시에 굴린다

- **Worktrees** — 격리된 git 체크아웃에서 세션을 따로 굴려 편집이 충돌하지 않게
- **세션 간 메시징** — 내가 띄운 세션들이 서로 발견을 전달하게
- **데스크톱 앱 / 웹 / Agent view** — 여러 세션을 시각적으로 관리하거나 클라우드·백그라운드에서 실행

병렬화 외에 **품질을 위한 용도**도 있습니다. **새 컨텍스트는 코드 리뷰를 개선합니다** — 방금 자기가 쓴 코드에 편향되지 않기 때문입니다. Writer/Reviewer 패턴:

| 세션 A (Writer) | 세션 B (Reviewer) |
| --- | --- |
| `API 엔드포인트용 레이트 리미터를 구현해줘` | |
| | `@src/middleware/rateLimiter.ts의 레이트 리미터 구현을 검토해줘. 엣지 케이스, 경쟁 상태, 기존 미들웨어 패턴과의 일관성을 봐줘.` |
| `리뷰 피드백이야: [세션 B 출력]. 이 문제들을 해결해줘.` | |

테스트에도 같은 구도를 쓸 수 있습니다 — 한쪽이 테스트를 쓰고, 다른 쪽이 그걸 통과하는 코드를 씁니다.

### 파일 단위로 펼친다 (fan out)

대규모 마이그레이션·분석은 병렬 호출로 분산합니다.

1. **작업 목록을 만들게 한다** — `마이그레이션이 필요한 Python 파일 2,000개를 나열해 files.txt에 저장해줘`
2. **목록을 도는 스크립트를 쓴다**

```bash
for file in $(cat files.txt); do
  claude -p "Migrate $file from Python 2 to Python 3. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)"
done
```

3. **2~3개로 먼저 시험하고** 프롬프트를 다듬은 뒤 전체를 돌립니다. `--allowedTools`로 할 수 있는 일을 제한하는 것이 **지켜보지 않는 실행에서 특히 중요합니다.**

기존 파이프라인에 끼워 넣을 수도 있습니다: `claude -p "<프롬프트>" --output-format json | your_command`

### 적대적 리뷰 단계를 넣는다

> **작업을 "완료"로 치기 전에, 새 컨텍스트의 서브에이전트에게 diff를 검토시키고 빠진 것을 보고받으세요.**

지켜보지 않는 시간이 길수록 **독립적인 확인**의 값이 올라갑니다. 새 컨텍스트의 리뷰어는 **diff와 내가 준 기준만** 볼 뿐 그 변경을 만든 추론 과정을 모르므로, 결과 자체로 평가합니다.

```text
서브에이전트로 레이트 리미터 diff를 PLAN.md와 대조해 검토해줘.
모든 요구사항이 구현됐는지, 나열된 엣지 케이스에 테스트가 있는지,
작업 범위 밖이 바뀌지 않았는지 확인해줘. 스타일 취향 말고 누락을 보고해줘.
```

⚠️ **빠진 것을 찾으라고 시킨 리뷰어는 대개 무언가를 찾아냅니다** — 작업이 멀쩡해도 그게 시킨 일이기 때문입니다. 모든 지적을 쫓으면 과잉 설계로 흐릅니다(불필요한 추상화 계층, 방어적 코드, 일어날 수 없는 경우의 테스트). **정확성이나 명시된 요구사항에 영향을 주는 누락만 지적하라**고 못 박고, 나머지는 선택 사항으로 취급하세요.

## 8. 흔한 실패 패턴

- **잡탕 세션** — 한 작업으로 시작해 관련 없는 걸 묻고 다시 원래 작업으로 돌아온다. 컨텍스트가 무관한 정보로 가득 찬다.
  **고치는 법:** 관련 없는 작업 사이에 `/clear`.
- **고치고 또 고치기** — 틀린 걸 고쳐줬는데 여전히 틀리고, 또 고쳐준다. 컨텍스트가 실패한 접근들로 오염된다.
  **고치는 법:** 두 번 실패하면 `/clear`하고, 배운 것을 반영한 더 나은 첫 프롬프트를 쓴다.
- **과잉 명세된 CLAUDE.md** — 너무 길어서 중요한 규칙이 소음에 묻히고 절반이 무시된다.
  **고치는 법:** 가차 없이 쳐낸다. 지시가 없어도 이미 잘한다면 지우거나 훅으로 바꾼다.
- **믿고 넘어가는 구멍** — 그럴듯해 보이지만 엣지 케이스를 처리하지 않은 구현이 나온다.
  **고치는 법:** 항상 검증 수단(테스트·스크립트·스크린샷)을 준다. **검증할 수 없으면 내보내지 않는다.**
- **끝없는 탐색** — 범위를 정하지 않고 "조사해줘"라고 시켜 수백 개 파일을 읽고 컨텍스트를 채운다.
  **고치는 법:** 조사 범위를 좁게 잡거나 서브에이전트에 맡겨 메인 컨텍스트를 지킨다.
