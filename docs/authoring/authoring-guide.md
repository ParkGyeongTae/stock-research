# 문서 작성 가이드

이 문서는 `docs/` 안에서 리서치 문서를 **쓰고 관리할 때** 지키는 규칙을 모아둡니다 — 폴더 구조·명명 규칙, 회사 폴더 파일별 역할(00~10 번호 체계), 작성 규칙, 신규 추가 절차, 로컬 확인까지 여기서 다룹니다. 주 독자는 `docs/`를 쓰고 관리하는 사람(Claude Code 등 에이전트)이지만, **저장소 주인이 "이 문서들이 어떤 규칙으로 만들어졌는지"를 사이트에서 읽을 수 있도록** 절차서도 `docs/authoring/`에 두고 함께 발행합니다 — 사이트 첫 페이지는 [`index.md`](../index.md)입니다.

---

## 📁 폴더 구조·명명 규칙

**`sectors/` 아래에 산업/섹터 폴더**, 그 아래에 회사 폴더를 둡니다. 리서치 콘텐츠는 전부 `sectors/` 한 곳에 모여 있고, 특정 회사·섹터에 종속되지 않는 참고 문서(`glossary.md`·`concepts/`·`macro/`)와 저장소 운영 절차서(`authoring/`)는 `docs/` 바로 아래에 나란히 둡니다 — **폴더 구조와 좌측 내비게이션이 같은 모양이 되도록** 중간 묶음 폴더를 두지 않습니다.

```
stock-research/
├── AGENTS.md              # 에이전트 역할·행동 지침 (CLAUDE.md는 이 파일의 심볼릭 링크)
├── README.md              # 레포 설명 (GitHub용)
├── .claude/skills/        # 문서 작성 절차를 코드화한 스킬 (SKILL.md + reference/)
├── scripts/               # 차트·재무 수치 생성 스크립트
└── docs/
    ├── .pages             # 최상위 nav 순서·표시 이름 (awesome-pages 플러그인)
    ├── index.md           # 사이트 첫 페이지 — 소개·커버리지 범위만 담은 환영 페이지
    ├── glossary.md        # PER/PBR/DCF/WACC 등 문서 전반에서 쓰는 용어 정리 (빠른 참조용)
    ├── concepts/          # glossary.md 용어를 예시로 풀어 쓴 학습용 문서 (공부용)
    ├── macro/             # 여러 회사 문서가 공통으로 인용하는 거시지표 차트 — 통화·금리·채권·주가지수·금속·에너지·디지털자산 서브폴더로 나뉨
    ├── authoring/         # 이 저장소를 굴리는 규칙과 AI 활용 참고 자료 (5편, 읽는 순서대로 .pages에 배열)
    │   └── template/company/   # 새 회사 추가 시 복사해서 쓰는 템플릿 11종 — 사이트에도 "회사 문서 템플릿"으로 발행됨
    └── sectors/           # 모든 섹터/회사 리서치 콘텐츠가 이 아래에 모임
        ├── .pages         # 섹터 nav 순서 — 새 섹터는 여기 등록해야 사이트에 노출됨 (아래 참고)
        └── <sector>/      # 섹터 폴더명은 풀어 쓴 소문자 스네이크케이스 (예: electronic_design_automation) — 그 아래에 회사별 폴더
            ├── 00_glossary.md  # (선택) 그 섹터에서만 쓰는 지표 정의. 필요한 섹터에만 둔다 (아래 참고)
            └── <company>/      # 회사 폴더
```

- **`docs/authoring/`의 다섯 편은 넓은 것에서 좁은 것 순으로 배열한다** — `claude-code-guide.md`·`codex-guide.md`(도구 사용법) → `skill-authoring-guide.md`(도구를 이 저장소에 맞게 확장) → `authoring-guide.md`(이 문서, 저장소 규칙의 마스터) → `chart-generation-guide.md`(그중 한 절차). 규칙을 읽고 나서 보는 실물이라 **회사 문서 템플릿(`template/company/`)은 그 뒤에 붙인다.** **순서는 `.pages`가 정하므로 문서를 추가할 땐 이 흐름의 어디에 들어가는지부터 정한다.**
- **성격이 둘로 갈린다** — 앞 둘은 외부 자료(Anthropic·OpenAI 공식 문서)를 정리한 **학습 참고용**이고, 뒤 셋은 이 저장소가 실제로 **지키는 규칙**이다. 참고용 문서는 첫 문단에 "규칙이 아니라 참고용"임을 밝힌다. 리서치 콘텐츠는 아니지만 **"이 사이트의 문서들이 어떤 규칙으로 만들어졌는지"를 읽을 수 있게** 함께 발행하며, 다른 발행 문서와 같은 규칙(`.md` 파일 직접 링크·`*작성일*` 표기)을 지킨다.
- **`AGENTS.md`만 저장소 루트에 남는다** — 에이전트가 세션 시작 시 루트에서 찾는 파일이고 `CLAUDE.md`가 그 심볼릭 링크라, 옮기면 지침 로딩이 끊긴다. 발행 문서에서 `AGENTS.md`를 가리킬 땐 상대 경로 대신 GitHub 절대 URL을 쓴다 — `docs/` 밖이라 상대 링크는 빌드 경고와 함께 깨진 채로 배포된다.
- **용어 정의는 쓰이는 범위에 따라 자리가 갈린다** — 여러 섹터에 두루 쓰이면 `glossary.md`, 한 섹터 안에서만 쓰면 그 섹터의 `00_glossary.md`다. `docs/` 직속 참고 문서는 "특정 회사·섹터에 종속되지 않는다"가 입주 기준이라, 섹터 전용 용어가 글로서리에 쌓이면 그 기준이 깨지고 다른 14개 섹터를 쓰는 사람이 매번 그 분량을 지나가게 된다. 자세한 판정 기준은 아래 "섹터 전용 용어" 참고.
- `docs/` 직속 참고 문서끼리도 성격이 갈린다: **`glossary.md`·`concepts/`는 읽는 문서**, **`macro/`는 여러 회사 문서가 공통으로 인용하는 거시지표 차트**(개별 회사·섹터의 밸류에이션 판단은 담지 않음), **`authoring/`은 이 저장소를 굴리는 절차서**(복사해서 쓰는 스캐폴딩인 `template/`도 그 아래에 둔다)다 — `sectors/`와 같은 층에 있는 이유는 모두 "특정 회사·섹터에 종속되지 않는다"는 기준을 만족하기 때문이다.
- `macro/` 하위는 성격별 서브폴더(`foreign_exchange/`·`rates/`·`bonds/`·`equities/`·`metals/`·`energy/`·`cryptocurrency/`)로 나뉜다. **`rates/`는 실제 거래되는 자산이 아닌 순수 금리·수익률(%), `bonds/`는 실제 거래되는 채권 ETF 가격($)**으로 갈린다. 각 문서는 `09_technical_daily.md`·`10_technical_weekly.md`와 같은 스크립트로 생성 — 작성법은 [`chart-generation-guide.md`](./chart-generation-guide.md) "주가가 아닌 시계열에 쓰기" 참고.
- 섹터 폴더명은 **풀어 쓴 소문자 스네이크케이스**(예: `electronic_design_automation`), 회사 폴더명은 **회사명 소문자 스네이크케이스**(예: `synopsys`) — 약어보다 명확한 전체 표기 우선.
- 복합기업은 "관심 이유"가 되는 사업 기준 섹터에 배치 (예: Siemens → `sectors/electronic_design_automation/`).
- **`.pages` 등록 규칙 (경고 없이 조용히 실패하므로 주의):**
    - 새 **섹터 폴더** → `docs/sectors/.pages`의 `nav:`에 추가해야 좌측 내비게이션에 노출된다. 등록하지 않아도 빌드는 성공하고 검색에도 잡히지만 nav에서만 사라져 사실상 고아 페이지가 된다(에러·경고 없음).
    - 새 **회사 폴더**(기존 섹터 안) → 등록 불필요, 자동으로 들어온다.
    - 새 **`docs/` 직속 문서·폴더**(`glossary.md`·`concepts/`·`macro/`·`sectors/` 옆) → `docs/.pages`의 `nav:`에 추가한다. 여기 `nav:`는 나열된 것만 노출하므로, 빠뜨리면 경고 없이 내비게이션에서 사라진다.
    - 새 `macro/` **하위 카테고리 폴더** → `docs/macro/.pages`에 추가. 기존 카테고리 안에 문서만 추가할 땐 그 카테고리의 `.pages`(예: `docs/macro/foreign_exchange/.pages`)에 추가한다.
- **`authoring/template/company/`는 `docs/`에서 정확히 3단계 깊이여야 한다.** 템플릿 안의 상대 링크(`../../../glossary.md` 등)는 **복사된 위치**(`docs/sectors/<sector>/<company>/` — 역시 3단계)를 기준으로 쓰였는데, 템플릿 폴더도 같은 깊이라 발행된 페이지에서도 그대로 맞는다. 옮기면 양쪽 다 깨진다.
- **템플릿 자리표시자는 `<n>`·`<X>`·`<YYYY-MM-DD>`처럼 ASCII 문자로 시작하면 백틱으로 감싼다.** 감싸지 않으면 Markdown이 HTML 태그로 보고 **본문에서 통째로 지워버려** 발행된 템플릿 페이지에 구멍이 생긴다(`<시가총액 기준일>`처럼 한글로 시작하면 태그로 파싱되지 않아 그냥 둬도 된다).
- **`template/` 폴더 안(`company/`의 형제 위치)의 `.pages`는 `company/` 안에 두지 않는다.** 회사 폴더를 만들 때 `cp -r`로 통째로 복사되면서 새 회사의 내비게이션 이름까지 "회사 문서 템플릿"으로 덮어쓰기 때문이다.

## ✍️ 작성 규칙

- 모든 문서는 **최상단에 `#` 제목 + `>` 한 줄 요약(투자 관점)**으로 시작
- 재무·실적 수치는 **기준 시점을 반드시 명시** (예: "FY2026 1분기 기준")
- 사실 정보(실적·인수·인물)는 **출처 링크를 그 수치·서술이 나오는 지점의 각주로** 남기기 — 문서 하단에 "참고 자료" 목록을 따로 두지 않는다(같은 링크를 두 번 관리하게 되고 본문과 어긋나기 쉽다)
- 저장소 안의 다른 문서를 링크할 땐 **폴더가 아니라 `.md` 파일을 직접** 가리키기 (`../rocket_lab/` ❌ → `../rocket_lab/01_overview.md` ✅) — 폴더 링크는 MkDocs가 해석하지 못하고 빌드 경고만 남긴 채 깨진 링크로 배포된다
- **본문에서 원본 파일명을 노출하지 않는다** — 이 문서들은 웹으로 발행되며 독자는 `04_metrics.md` 같은 파일명을 본 적도 없다. 대신 그 문서의 `#` 제목("핵심 지표", "밸류에이션 / 적정주가")으로 쓰고, **절을 가리킬 땐 번호만이 아니라 실제 절 제목까지** 적는다(번호만으로는 내용을 알 수 없고, 원 문서의 절 구성이 바뀌면 조용히 어긋난다). 링크가 필요하면 파일명을 표시 텍스트 밖 URL에만 둔다.
    - ❌ "`06_valuation.md` §4-B 참고" / ❌ "밸류에이션 / 적정주가 §4-B 참고"
    - ✅ "밸류에이션 / 적정주가 4-B. PER/PBR 민감도 참고" / ✅ `[밸류에이션 / 적정주가](./06_valuation.md)`
    - 이 규칙은 파일 구조를 설명하는 메타 텍스트(이 문서, 템플릿의 작성자 지침 블록)에는 적용하지 않는다 — 지침 블록은 발행 시점에 이미 문서에 없다.
- 주관적 판단(투자 결론)과 객관적 사실(재무 수치)을 **섞지 말고 구분**해서 적기
- 회계연도(FY)처럼 헷갈리는 개념은 각주로 설명 — 예: "FY2026 1분기 = 2025-11 ~ 2026-01. Synopsys는 10월 결산이라 캘린더 연도와 어긋난다."
- 커버리지 기본 전제는 **미국 상장 기업(NYSE/NASDAQ, USD 표시)** — 템플릿의 재무·거버넌스 용어(GAAP/Non-GAAP, 위임장(Proxy Statement) 등)도 이 전제 위에서 작성됐다. 비-US 기업을 예외로 다룰 땐 해당 용어를 그 회사 문서 안에서 치환하고 상단 인용문 아래 이탤릭 한 줄로 남긴다: `*이 회사는 유럽 상장이라 IFRS를 사용. 이하 표의 "GAAP"은 모두 IFRS로 읽는다.*`
- **표기법이 곧 "발행 여부"를 뜻한다** — `>` 인용 블록은 **작성자용 지침이라 발행 전에 지우고**, `!!! …`·`??? …`(Material admonition)는 **독자가 읽을 내용이라 남긴다.** 문서를 다 채운 뒤 `> ⚠️`가 하나라도 남아 있으면 아직 발행 준비가 안 된 것이다. 독자에게 보여줄 내용은 성격에 따라 나눠 쓴다:
    - `!!! warning "…"` — **꼭 보고 넘어가야 하는 것.** 이 회사 고유의 오독 위험(분할 소급조정, 일회성 손익, 짧은 상장 이력), 투자 권유가 아니라는 고지. 펼쳐진 채로 둔다.
    - `??? note "…"` — **필요할 때만 펼쳐 보는 참조 정보.** 통화 단위·회계기준·(E) 표기·평균 산정 구간 같은 "표를 읽는 전제". 접혀 있어 본문 진입을 막지 않는다.
    - 이 구분이 없으면 전제와 경고가 한 덩어리로 문서 머리를 막는다 — 실제로 `04_metrics.md`는 본문 첫 절까지 24줄이 전부 경고 블록이던 시기가 있었다.
- **템플릿에서 온 작성자 지침 블록(`> ⚠️ …`)은 발행 전에 지운다.** 회사 문서 전부(`00`~`10`)에 적용된다. 다만 모든 `>` 블록을 지우라는 뜻은 아니다 — "이 회사 고유의 주의사항을 여기 적으라"고 자리를 가리키는 블록은 지우는 대신 **실제 내용으로 교체**한다. 판별 기준: **이 회사 고유의 사실이 하나도 안 들어간 일반론이면 지운다.**
    - 지운다 ❌ "모든 항목은 웹검색으로 확인한 사실만 기록. 추측이나 출처 불명 내용은 작성 금지"
    - 남긴다 ✅ "이 회사는 표 기간 내 두 차례 분할이 있었다 — 2022-09 3:1, 2024-12-16 2:1. 아래 표의 주가·EPS는 조정 후 기준"
- 문서 맨 아래에 `*작성일: YYYY-MM-DD*` 표기 — **날짜는 항상 하나만, 그 문서를 마지막으로 손댄 날(=오늘)로 교체한다.** 옛 날짜를 남기거나 `(최종 수정일: …)`을 덧붙이지 않고, 무엇을 고쳤는지도 적지 않는다 — 변경 이력의 원 출처는 git log다. **이 표기는 발행 문서(`docs/**`)에 적용한다.** `docs/authoring/`의 절차서도 발행 문서라 이 표기를 지킨다. **예외는 `authoring/template/company/`뿐이다** — 발행되긴 하지만 채워 넣을 뼈대라 `*작성일: YYYY-MM-DD*`를 자리표시자 그대로 둔다. 저장소 루트에 남는 `AGENTS.md`는 git log가 이력을 그대로 대신하므로 표기하지 않는다.

### 회사 문서 파일 규율 (통일 규칙)

회사 폴더 안 파일은 아래 전부가 **필수**다.

파일명 앞 숫자(00~10)는 **읽는 순서**를 그대로 나타내며, 내비게이션 순서도 이 숫자가 정한다(회사 폴더에는 `.pages`를 두지 않는다 — 두면 아직 파일이 없는 작성 중 폴더에서 `NavEntryNotFound`로 **빌드가 실패한다**). `08_news.md`는 핵심 분석 흐름(01~07) 완성 후에 붙는 로그, `09`·`10`은 펀더멘털 판단과 별개인 가격 패턴 참고 자료라 뒤에 둔다.

**`00_final_report.md`만 읽는 순서와 쓰는 순서가 반대다.** 나머지 10개를 전부 인용하는 자기완결 요약본이라 **읽을 땐 맨 처음**(이 문서 하나로 회사 전체를 파악할 수 있어야 하고, 사이트 방문자도 여기서 시작한다)이지만 **쓸 땐 가장 마지막**이다 — `01`~`10`이 아직 안 채워졌거나 최신 상태가 아니면 이 파일부터 쓰지 않는다. 번호가 `00`이라고 먼저 쓰지 말 것.

회사마다 파일을 **똑같은 이름**으로 유지하면 나중에 회사 간 비교가 쉬워진다.

`04_metrics.md`가 원자료의 유일한 출처다. `05`·`06`·`07`·`00`은 숫자를 다시 채우지 말고 그 값을 인용해 해석만 쓴다. `06_valuation.md`의 미래 추정치(E)처럼 `04_metrics.md`에 아직 없는 값만 그 문서에 직접 근거를 남기고, 확정치는 항상 `04_metrics.md`로 되돌아가 채운다.

문서 간 이동은 사이트 좌측 내비게이션이 담당한다 — 본문 하단에 다른 문서로의 링크 목록을 따로 만들지 않는다(2026-08-27 "관련 문서"·"참고 자료" 절 폐지). 본문 안에서 맥락상 필요한 링크만 남긴다.

PER·PBR·DCF·WACC·%p 등 용어가 낯설면 [`glossary.md`](../glossary.md)를 먼저 본다.

### `04_metrics.md` 절 구조

- **A. 연간 표** — 최근 3개년 + 올해. 실적(A.1)·밸류에이션(A.2)·재무 건전성(A.3)·현금흐름과 주주환원(A.4)으로 나뉘며, 평균·중앙값 비교의 기준이 된다.
- **B. 분기 표** — 최근 6개 분기. 계절성·최근 추세를 보기 위한 별도 표.
- **C. 사업 고유 지표** — backlog·ARR·거래대금 등. 규칙은 아래 "사업 고유 지표" 참고. 단순한 사업이면 절을 통째로 삭제하고 A절 상단 각주에 사유를 남긴다.
- **D. 판단 메모** — 표 대비 위치·추세를 짧게 확인한다. **왜 그런지의 서술적 해석은 여기 쓰지 말고 `05_financials.md`로.** 여기서는 "매출성장률이 최근 3분기 연속 감소" 같은 관측만 남긴다.

A·B절의 GAAP 수치는 공시를 눈으로 옮겨 적지 말고 `scripts/fetch_sec_facts.py`로 가져옵니다 — SEC가 회사로부터 XBRL로 받아둔 값을 한 번에 뽑아 주고, 이 저장소가 반복해서 혼동하던 **지배주주 귀속 vs 연결(NCI 포함)**·**부채총계 vs 이자부 차입금**을 각각 별도 행으로 줍니다. 사용법과 한계(Non-GAAP은 XBRL에 없음, Q4는 파생)는 그 스크립트의 docstring이 마스터입니다. 종가·시가총액·베타·컨센서스·사업 고유 지표는 스크립트 범위 밖이라 따로 조사합니다.

증감액·증감폭(%p) 행은 두지 않는다 — 잔액 행에서 바로 도출되는 값이라 채우는 만큼 어긋날 여지만 는다. 비교는 증감률(%)로 한다.

### 숫자를 다룰 때 반드시 지키는 것

문서 간에 숫자가 어긋나는 사고는 대부분 아래 다섯 가지에서 납니다. 정의는 [`glossary.md`](../glossary.md), 예시 풀이는 [`concepts/`](../concepts/financial-metrics.md)에 있습니다.

1. **할인율과 현금흐름의 짝** — `04_metrics.md`의 FCF(`CFO − CapEx`)는 지급이자가 이미 빠진 **Levered FCF**(≈ FCFE)다. DCF에서 이 값을 할인할 땐 **자기자본비용(Ke)**을 쓰고 순부채를 따로 빼지 않는다. WACC를 쓰려면 현금흐름을 FCFF(≈ EBIT×(1−t) + D&A − CapEx − ΔWC)로 바꾸고 마지막에 순부채를 차감해야 한다 — **섞으면 결과가 틀린다.** 정통 FCFE는 여기에 Net Borrowing(신규 차입 − 상환)을 더한 값이므로, 표 기간에 순차입이 크게 변한 회사(대규모 자사주매입용 차입, 대규모 채무상환)는 그 해만 별도 보정하거나 FCFF+WACC 프레임으로 통일하는 편이 안전하다.
2. **GAAP / Non-GAAP 구분** — 행마다 어느 기준인지 표기. 둘의 차이가 무엇으로 채워져 있는지(SBC / 인수 무형자산 상각 / 일회성)를 각주로 분해할 것. 반복되는 SBC를 "일회성 제거"로 읽지 않는다.
3. **부채총계 vs 이자부 차입금** — 정의는 [`glossary.md`](../glossary.md) "부채비율"·"순부채" 참고, 두 값을 섞지 않는다. ⚠️ 미국 10-K의 **D/E ratio**는 대개 이자부 차입금 ÷ 자기자본을 가리켜 이 레포의 부채비율 정의(부채총계 기준)와 다르다 — 10-K가 보고한 D/E 값을 그대로 "부채비율" 열에 옮기지 말 것.
4. **평균·중앙값에 추정치(E)를 섞지 않는다** — 확정치만으로 계산하고, 몇 개년 기준인지 각주에 남긴다.
5. **주식분할 소급조정** — 표 기간 내 분할·병합이 있었으면 과거 전 구간(주가·EPS·BPS·DPS·주식수)을 조정 후 기준으로 맞춘다.

### 사업 고유 지표 (`04_metrics.md` C절)

표준 재무 지표만으로는 그 회사의 동력이 안 잡히는 경우가 있습니다 — 방산의 **수주잔고·book-to-bill**, 구독 소프트웨어의 **ARR·NRR·RPO**, 플랫폼의 **거래대금·테이크레이트**, 금융의 **AUC·예치금 운용수익(float)** 같은 것들입니다. 정의는 [`glossary.md`](../glossary.md) "5. 사업 모델 · 성장 지표"에 있습니다.

1. **지표는 회사가 아니라 섹터 단위로 정한다** — 같은 섹터의 모든 회사가 같은 지표를 채워야 비교가 됩니다. 섹터의 표준 지표는 첫 회사의 C절에서 정하고, 다음 회사가 그대로 따릅니다.
2. **최대 5개** — IR이 자랑하는 지표를 다 옮기면 갱신이 안 돼 금방 낡습니다. "이 숫자가 나빠지면 투자 논거가 흔들리는가"로 고릅니다.
3. **정의를 반드시 병기** — 같은 이름이 회사마다 다른 것을 가리킵니다(backlog의 funded 포함 여부, ARR에 포함되는 계약 범위, NRR의 고객 수 기준 vs 금액 기준). 회사 공시 정의를 그대로 적습니다.
4. **잔고(stock)형 지표는 평균·중앙값을 내지 않는다** — backlog·AUC·이연수익처럼 "특정 시점의 잔량"은 기간 평균이 의미가 없어 해당 열을 `—`로 둡니다. book-to-bill·거래대금 같은 유량(flow)만 평균을 냅니다.
5. **없는 지표면 용어 문서를 먼저 갱신** — 회사 문서에서 용어를 새로 정의하지 않습니다. 어느 파일에 넣을지는 아래 "섹터 전용 용어"의 판정 기준을 따릅니다.

### `00_final_report.md` 작성 규칙

`authoring/template/company/00_final_report.md`를 복사해서 쓴다. 다른 파일과 달리 이 문서는 **새 사실·새 판단을 만들지 않고, `01~10`과 `macro/`의 관련 문서를 종합·요약만** 한다.

1. **가장 마지막에 쓴다** — 01~10이 최신이 아니면 작성을 미룬다. 이후 01~10 중 하나라도 갱신되면(특히 `04`·`06`·`07`) 이 문서도 갱신 대상이다 — [`AGENTS.md`](https://github.com/ParkGyeongTae/stock-research/blob/main/AGENTS.md) "작업을 마치기 전에"의 인용처 추적에 이 문서를 포함시킬 것.
2. **`01`~`10`을 열지 않아도 판단이 서게 쓰되, 전재(全載)하지 않는다** — 이 보고서만 읽는 독자를 기준으로 삼는다. 회사가 무엇을 하는지, 어떻게 지금 모습이 됐는지(연혁·경영진), 숫자가 어떤 상태인지(표준 지표 + 사업 고유 지표), 무엇이 결론을 지탱하는지(해자)와 뒤집는지(리스크)가 전부 이 안에 있어야 한다. 다만 절이 늘어난 만큼 원 문서와 어긋날 표면적도 늘어나므로, 옮길지 말지는 **"그것을 빼면 시나리오 요약의 결론이 이해되지 않는가"**로 판정한다 — 분기 시계열·민감도 격자·방법론 계산 과정·연혁 전체는 원 문서에 남긴다.
3. **거시 환경에 넣을 macro 문서는 회사마다 다르게 고른다** — 7개 카테고리를 전부 나열하지 않는다. 매출·매입원가가 특정 원자재·환율에 연동되는지, `06_valuation.md`의 할인율이 금리에 근거하는지(대부분 해당), 지수 대비 상대 성과를 봐야 하는지로 고른다. 인용하는 macro 문서의 차트가 낡았다면 이 문서를 쓰기 전에 먼저 갱신한다 — 최종 보고서 안에서 새 차트를 만들지 않는다.
4. **시나리오 요약은 새 계산이 아니라 재배치다** — `06_valuation.md`의 가격(하방/기본/상방)과 `07_investment.md`의 리스크(트리거)를 한 표로 합칠 뿐이다. 상방 시나리오가 원 문서에 없으면 그 행을 비워두지 말고 통째로 뺀다.
5. **최종 매수/매도 트리거를 새로 만들지 않는다** — 최종 결론은 `07_investment.md` "4. 투자 결론"을 인용하되 시나리오 표를 근거로 한 문장만 덧붙인다. 새 판단이 떠올랐다면 먼저 원 문서에 반영한 뒤 여기서 인용한다.
6. **회사 폴더 안(`01`~`10`)의 링크·인용을 본문에 넣지 않는다** — 위 "✍️ 작성 규칙"의 파일명 노출 금지보다 한 단계 더 엄격하다. "→ 상세: 핵심 지표" 같은 줄도, "(기술적 분석 참고)" 같은 괄호 인용도 넣지 않는다. 다른 절을 가리켜야 하면 "위 5. 밸류에이션 결론에서 보듯"처럼 **이 보고서 자체의 절**로 참조한다 — 링크 없이도 읽히는 자기완결 요약본이어야 한다. **예외는 거시 환경 절의 macro 문서 링크뿐이다** — 회사 폴더 밖의 공용 차트라 이 보고서가 요약할 대상이 아니고, 독자가 원본 차트로 건너갈 수단이 필요하다.

### `glossary.md` · `concepts/` 작성 규칙

두 문서는 역할이 다릅니다 — **`glossary.md`는 정의, `concepts/`는 근거**입니다. 이 경계가 흐려지면 같은 내용이 두 곳에서 따로 낡고, 나중에 어디를 고쳐야 할지도 헷갈립니다.

1. **정의는 글로서리에, 예시·근거는 concepts에** — 글로서리 셀은 1~2문장으로 끝내고 "왜 그런가"나 계산 예시는 셀 안에 다시 쓰지 않습니다. concepts에 아직 근거가 없다면 먼저 그쪽에 쓰고 글로서리에서 링크합니다.
2. **1:1 매핑을 유지합니다** — `concepts/`의 파일들은 `glossary.md`의 절 번호(1~10)에 정확히 대응합니다. 새 개념이 생기면 새 파일을 만들지 말고 해당 절의 파일에 `##` 절을 추가합니다.
3. **예시 수치는 반드시 검산합니다** — 실제로 대입해 계산이 맞는지 확인한 뒤 커밋합니다. 특히 식을 거꾸로 푸는 예시(역DCF 등)는 구한 값을 원래 식에 다시 대입해 검증합니다.
4. **concepts는 평생 참고용입니다** — "2026년 현재" 같은 시점 서술을 넣지 않습니다. 시점에 따라 달라지는 값(금리·물가 등)은 원출처를 가리키고 이 문서에는 적지 않습니다.
5. **섹터 전용 용어는 글로서리에 넣지 않습니다** — 아래 규칙을 따릅니다.

### 섹터 전용 용어 (`<sector>/00_glossary.md`)

한 섹터 안에서만 쓰는 지표는 `docs/sectors/<sector>/00_glossary.md`에 둡니다. 예: 자원개발의 **증명매장량·PV-10**, LNG의 **액화 능력·SPA**, 미드스트림의 **AFFO·Segment EBDA**, 항공우주의 **형식증명·PMA/USM**.

1. **판정 기준은 "지금 두 개 이상의 섹터가 쓰는가"입니다** — 쓰면 `glossary.md`, 아니면 섹터 파일입니다. "언젠가 다른 섹터도 쓸 것 같다"는 근거가 되지 않습니다. 실제로 두 번째 섹터가 쓰기 시작하면 그때 글로서리로 올립니다.
2. **필요한 섹터에만 만듭니다** — 전 섹터에 빈 파일을 미리 깔지 않습니다. 표준 지표만으로 충분한 섹터가 대부분입니다.
3. **정의만 담습니다** — 산업 분석·전망·경쟁 구도는 회사 문서 몫입니다(섹터 개요 문서는 폐지됐고, 이 파일은 그 부활이 아닙니다).
4. **만들면 그 섹터 폴더에 `.pages`를 함께 둡니다** — 없으면 회사 폴더들 사이에 섞여 나옵니다.

    ```
    nav:
      - 섹터 용어: 00_glossary.md
      - ...
    ```

5. **글로서리 5절 머리말에 링크를 추가합니다** — 섹터 파일을 새로 만들면 찾아갈 길이 있어야 합니다.

## ➕ 새 회사 추가 방법

```bash
# 1. 템플릿 복사 (이미 있는 회사를 다시 만드는 경우 폴더부터 지운다 — 아래 "재생성" 참고)
rm -rf docs/sectors/<sector>/<company-name>
cp -r docs/authoring/template/company docs/sectors/<sector>/<company-name>

# 2. 파일 내용 채우기 — 전부 필수, 삭제하지 않는다. 01~10을 먼저 채우고 11은 가장 마지막
```

**섹터 폴더에는 개요 문서를 두지 않는다.** 산업 밸류체인·시장 규모·구조적 리스크는 각 회사 `01_overview.md`의 "산업 / 시장 내 위치"에서 **그 회사 관점으로만** 다룬다. 섹터 폴더에 둘 수 있는 것은 회사 폴더와, 필요한 경우 정의만 담는 `00_glossary.md`뿐이다(위 "섹터 전용 용어" 참고).

`09_technical_daily.md`·`10_technical_weekly.md`의 SVG·레벨 표·방법론 수치는 손으로 만들지 말고 스크립트로 생성한다 — 커맨드·옵션·주의사항은 [`chart-generation-guide.md`](./chart-generation-guide.md) "기술적 분석 차트 생성"이 마스터다.

**재생성** — 이미 있는 문서를 고칠 때도 부분 수정하지 않고 위 절차 그대로 지우고 다시 만든다. 부분 수정하면 눈에 띄는 절만 고쳐지고 템플릿이 바뀐 뒤에도 옛 절 구성·옛 항목 수가 남는다. 다만 지우기 전에 **웹에서 다시 구할 수 없는 것**은 옮겨 적는다 — 뉴스 로그, `04_metrics.md`의 회사 고유 `!!! warning`(분할 소급조정 이력 등), 섹터 단위로 합의된 사업 고유 지표, `06_valuation.md`의 방법론 채택·제외 사유. 나머지는 전부 새로 조사한다.

**섹터 자체가 새로 생기는 경우에만** `docs/sectors/.pages`에 폴더명을 추가하는 단계가 더 있다(위 `.pages` 등록 규칙 참고). 기존 섹터에 회사만 추가할 땐 필요 없다.

### 로컬에서 확인하기

```bash
uv run mkdocs serve   # http://127.0.0.1:8000 에서 미리보기
uv run mkdocs build   # 배포와 동일하게 빌드 — 경고 메시지를 반드시 확인
```

`build` 출력의 `unrecognized relative link` 경고는 **깨진 문서 간 링크**를 뜻한다. 깨진 링크가 있어도 빌드는 성공하고 GitHub Actions 배포도 그대로 통과하므로, 문서를 추가·이동한 뒤에는 경고가 늘지 않았는지 직접 봐야 한다. nav 순서는 `awesome-pages` 플러그인이 `.pages` 파일과 파일명 숫자 접두사로 결정한다.
