# Codex 활용 가이드

이 문서는 OpenAI의 [Best practices (Codex)](https://learn.chatgpt.com/guides/best-practices)를 한국어로 정리한 것입니다. 이 저장소가 실제로 쓰는 도구는 Claude Code라 **규칙이 아니라 비교·참고용**이지만, `AGENTS.md`·스킬·MCP처럼 두 에이전트가 공유하는 개념이 많아 나란히 두고 읽을 값이 있습니다. Claude Code 쪽은 [Claude Code 활용 가이드](./claude-code-guide.md)에 있습니다.

---

Codex를 **일회성 비서보다 시간을 들여 설정하고 개선해 나가는 팀원**으로 다룰 때 가장 잘 동작합니다. 전체 흐름은 이렇습니다 — 작업에 맞는 컨텍스트로 시작하고, 지속적인 지침은 `AGENTS.md`에 담고, 작업 방식에 맞게 Codex를 설정하고, 외부 시스템은 MCP로 연결하고, 반복되는 일은 스킬로 만들고, 안정된 작업은 자동화합니다.

여기 나오는 습관은 CLI·IDE 확장·ChatGPT 데스크톱 앱 모두에 적용됩니다.

---

## 1. 첫 단추: 컨텍스트와 프롬프트

Codex는 프롬프트가 완벽하지 않아도 쓸 만한 결과를 냅니다 — 어려운 문제를 설정 없이 던져도 곧잘 풀어냅니다. **명확한 프롬프트는 필수가 아니라 신뢰도를 올리는 장치**입니다. 큰 코드베이스나 실수 비용이 큰 작업일수록 차이가 벌어집니다.

기본값으로 **네 가지**를 프롬프트에 담으세요.

- **Goal(목표)** — 무엇을 바꾸거나 만들려는가?
- **Context(맥락)** — 어떤 파일·폴더·문서·예시·에러가 이 작업에 관련되는가? (`@`로 파일을 지목할 수 있습니다)
- **Constraints(제약)** — 어떤 표준·아키텍처·안전 요구사항·관례를 따라야 하는가?
- **Done when(완료 조건)** — 무엇이 참이어야 끝난 것인가? (테스트 통과, 동작 변화, 버그 재현 안 됨 등)

이 네 가지가 있으면 Codex가 **범위를 벗어나지 않고, 가정을 덜 하고, 리뷰하기 쉬운 결과물**을 냅니다.

**추론 수준(reasoning level)은 작업 난이도에 맞춰 고르고, 자기 작업 흐름에서 뭐가 맞는지 시험해 보세요** — 사용자마다 작업마다 최적값이 다릅니다.

- **Low** — 빠르고 범위가 분명한 작업
- **Medium·High** — 복잡한 변경이나 디버깅
- **Extra High** — 길고 추론이 많이 필요한 에이전틱 작업

> 💡 맥락을 빠르게 전달하려면 ChatGPT 데스크톱 앱의 **음성 받아쓰기**로 원하는 것을 말해 보세요.

## 2. 어려운 작업은 계획부터

작업이 복잡하거나 모호하거나 말로 설명하기 어렵다면, **코딩을 시작하기 전에 계획을 세우게** 합니다. 세 가지 방법이 잘 통합니다.

- **Plan 모드** — 대부분의 사용자에게 가장 쉽고 효과적입니다. Codex가 맥락을 모으고, 명확히 할 질문을 던지고, 더 나은 계획을 만든 뒤 구현에 들어갑니다. `/plan` 또는 `Shift+Tab`으로 전환합니다.
- **나를 인터뷰하게 시키기** — 대충 원하는 건 있는데 잘 설명하지 못하겠다면, 먼저 나에게 질문하게 하세요. **내 가정을 반박하라고 시켜** 흐릿한 아이디어를 구체적인 것으로 바꾼 뒤 코드를 씁니다.
- **`PLANS.md` 템플릿** — 더 고급 흐름에서는 길거나 여러 단계인 작업에 `PLANS.md`(실행 계획) 템플릿을 따르도록 설정할 수 있습니다.

## 3. `AGENTS.md`로 지침을 재사용 가능하게 만든다

프롬프트 패턴이 한번 통했다면, 다음 단계는 **그걸 매번 손으로 반복하지 않는 것**입니다. `AGENTS.md`가 그 자리입니다.

`AGENTS.md`는 **에이전트를 위한 개방형 README**라고 생각하면 됩니다. 자동으로 컨텍스트에 로드되며, 이 저장소에서 Codex가 어떻게 일하기를 바라는지 적어 두기에 가장 좋은 곳입니다.

좋은 `AGENTS.md`가 담는 것:

- 저장소 구조와 중요한 디렉터리
- 프로젝트 실행 방법
- 빌드·테스트·린트 명령
- 엔지니어링 관례와 PR 기대치
- 제약과 **하지 말아야 할 것**
- **"완료"의 정의와 작업을 검증하는 방법**

CLI의 `/init`으로 현재 디렉터리에 초안을 만들 수 있습니다. 좋은 출발점이지만, **팀이 실제로 빌드·테스트·리뷰·배포하는 방식에 맞게 고쳐야** 합니다.

`AGENTS.md`는 여러 층위에 둘 수 있습니다 — 개인 기본값은 `~/.codex`의 전역 파일, 팀 공용 표준은 저장소 루트 파일, 국소 규칙은 하위 디렉터리 파일. **현재 디렉터리에 더 가까운 파일이 우선합니다.**

**실용적으로 유지하세요.** 모호한 규칙으로 가득한 긴 파일보다 **짧고 정확한 `AGENTS.md`가 낫습니다.** 기본부터 적고, **반복되는 실수를 관찰한 뒤에** 규칙을 추가합니다. 파일이 너무 커지면 본체는 간결하게 두고 계획·코드 리뷰·아키텍처 같은 작업별 마크다운 파일로 나눠 참조하게 합니다.

> 💡 Codex가 **같은 실수를 두 번** 하면 회고를 시키고 `AGENTS.md`를 갱신하세요. 그러면 지침이 실제 마찰에 근거해 쌓입니다.

## 4. 일관성을 위해 Codex를 설정한다

설정은 **세션과 환경(CLI·IDE·데스크톱 앱)이 바뀌어도 동작을 일관되게** 만드는 주요 수단입니다. 모델 선택, 추론 강도, 샌드박스 모드, 승인 정책, 프로필, MCP 설정의 기본값을 정할 수 있습니다.

- **개인 기본값** → `~/.codex/config.toml`
- **저장소별 동작** → `.codex/config.toml`
- **명령줄 오버라이드** → 일회성 상황에만

`config.toml`에는 MCP 서버, 멀티 에이전트 구성, 기능 플래그 같은 지속적 선호를 정의합니다. 프로필별 오버라이드는 `$CODEX_HOME/프로필이름.config.toml`에 따로 둡니다.

Codex는 **OS 수준 샌드박싱**을 기본 탑재하며 조절 손잡이가 둘입니다.

- **승인 모드(approval mode)** — 명령 실행 전에 언제 물어볼지
- **샌드박스 모드(sandbox mode)** — 디렉터리를 읽고 쓸 수 있는지, 어떤 파일에 접근할 수 있는지

**코딩 에이전트가 처음이라면 기본 권한으로 시작하세요.** 승인과 샌드박스를 조여 둔 채로 쓰다가, 필요가 분명해진 신뢰할 수 있는 저장소·작업에서만 풀어 줍니다. CLI·IDE 확장·데스크톱 앱은 **같은 설정 계층을 공유합니다.**

> 💡 **실제 환경에 맞춰 일찍 설정하세요.** 품질 문제로 보이는 것들이 사실은 설정 문제인 경우가 많습니다 — 잘못된 작업 디렉터리, 쓰기 권한 없음, 모델 기본값 오설정, 도구·커넥터 누락.

## 5. 테스트와 리뷰로 신뢰도를 올린다

**변경을 시키는 데서 멈추지 마세요.** 필요하면 테스트를 만들고, 관련 검사를 돌리고, 결과를 확인하고, 받아들이기 전에 스스로 리뷰하게 합니다.

Codex는 이 루프를 대신 돌 수 있지만, **"좋은 상태"가 무엇인지 알 때만** 가능합니다. 그 기준은 프롬프트나 `AGENTS.md`에서 옵니다. 루프에 넣을 것:

- 변경에 대한 테스트 작성·갱신
- 알맞은 테스트 스위트 실행
- 린트·포매팅·타입 검사
- 최종 동작이 요청과 맞는지 확인
- 버그·회귀·위험한 패턴 관점에서 diff 리뷰

`/review` 슬래시 명령이 몇 가지 리뷰 방식을 제공합니다 — **기준 브랜치와 비교하는 PR 방식 리뷰**, 커밋되지 않은 변경 리뷰, 특정 커밋 리뷰, 사용자 지정 리뷰 지침 사용.

팀에 `code_review.md`가 있고 `AGENTS.md`에서 그것을 참조한다면 Codex가 리뷰 때도 그 지침을 따릅니다. **저장소와 기여자가 달라져도 리뷰 기준을 일정하게 유지하려는 팀에 강력한 패턴입니다.**

GitHub Cloud를 쓴다면 PR에 Codex 코드 리뷰를 붙일 수 있습니다 — 자동 리뷰를 켜거나 `@Codex`로 호출하는 방식입니다. **OpenAI 내부에서는 Codex가 PR의 100%를 리뷰합니다.**

## 6. 외부 컨텍스트는 MCP로 가져온다

**Codex에 필요한 맥락이 저장소 밖에 있을 때** MCP(Model Context Protocol)를 씁니다. 이미 쓰는 도구·시스템에 연결해 두면 살아 있는 정보를 매번 복사해 붙여넣지 않아도 됩니다.

MCP를 쓸 때:

- 필요한 맥락이 저장소 밖에 있을 때
- 데이터가 자주 바뀔 때
- 붙여넣은 지시가 아니라 **도구를 직접 쓰게** 하고 싶을 때
- 사용자·프로젝트를 넘어 재현 가능한 통합이 필요할 때

Codex는 STDIO와 Streamable HTTP(OAuth 포함) 서버를 모두 지원합니다. 데스크톱 앱은 **Settings > MCP servers**, CLI는 `codex mcp add`로 추가합니다.

> 💡 **실제 작업 흐름을 열어 주는 도구만 붙이세요.** 쓰는 도구를 전부 연결하며 시작하지 말고, **이미 자주 반복하는 수작업 루프를 확실히 없애 주는 한두 개**로 시작해 넓혀 갑니다.

## 7. 반복되는 일은 스킬로 만든다

작업 흐름이 반복되기 시작하면 긴 프롬프트나 왕복 대화에 기대지 말고 **스킬**로 포장합니다 — `SKILL.md`에 지시·맥락·보조 로직을 담아 Codex가 일관되게 적용하게 하는 것입니다. 스킬은 CLI·IDE 확장·데스크톱 앱에서 모두 동작합니다.

- **스킬 하나는 하나의 일만** 맡깁니다
- 구체적인 사용 사례 **2~3개**로 시작하고, 입력과 출력을 분명히 정합니다
- **description에는 무엇을 하는지와 언제 쓰는지**를 적고, **사용자가 실제로 말할 법한 트리거 표현**을 넣습니다
- 엣지 케이스를 처음부터 다 덮으려 하지 마세요 — 대표 작업 하나를 잘 되게 만든 뒤 그것을 스킬로 굳히고 개선합니다
- 스크립트나 부가 자산은 **신뢰도가 올라갈 때만** 넣습니다

**판단 기준:** 같은 프롬프트를 계속 재사용하거나 같은 작업 흐름을 계속 교정하고 있다면, 그건 스킬이 돼야 할 것입니다.

잘 맞는 반복 작업: 로그 분류, 릴리스 노트 초안, 체크리스트 기반 PR 리뷰, 마이그레이션 계획, 텔레메트리·인시던트 요약, 표준 디버깅 흐름.

첫 버전은 `$skill-creator` 스킬로 뼈대를 잡고, 다듬는 동안은 로컬에 두다가 널리 공유할 준비가 되면 플러그인으로 패키징합니다.

> 💡 개인 스킬은 `$HOME/.agents/skills`, 팀 공용 스킬은 저장소 안 `.agents/skills`에 체크인합니다 — 새 팀원 온보딩에 특히 유용합니다.

## 8. 안정된 작업은 예약 실행으로 넘긴다

작업 흐름이 안정되면 백그라운드에서 주기적으로 돌리게 할 수 있습니다. 데스크톱 앱의 **Scheduled** 페이지에서 프로젝트·프롬프트·주기·실행 환경(전용 Git worktree 또는 로컬 환경)을 고릅니다. 프롬프트 안에서 스킬을 호출할 수도 있습니다.

좋은 후보: 최근 커밋 요약, 버그 가능성 스캔, 릴리스 노트 초안, CI 실패 확인, 스탠드업 요약, 주기적 분석 작업.

**유용한 원칙: 스킬은 *방법*을 정의하고, 예약 작업은 *시점*을 정의합니다.** 아직 손이 많이 가는 작업이라면 먼저 스킬로 만들고, 예측 가능해진 다음에 예약합니다.

> 💡 예약 작업을 **실행뿐 아니라 회고·정비**에도 쓰세요 — 최근 대화를 검토해 반복되는 마찰을 요약하고, 프롬프트·지침·설정을 개선해 나가는 용도입니다.

## 9. 긴 대화를 관리한다

대화에는 맥락·결정·행동이 쌓이므로 **관리 방식이 품질에 크게 영향**을 줍니다. 데스크톱 앱에서는 대화를 고정(pin)하고 worktree를 만들 수 있습니다. CLI에서 특히 유용한 슬래시 명령:

- `/experimental` — 실험 기능을 켜고 `config.toml`에 반영
- `/resume` — 저장된 대화 이어서 하기
- `/fork` — 원래 기록을 보존한 채 새 대화 만들기
- `/compact` — 대화가 길어졌을 때 이전 맥락을 요약본으로 (자동 압축도 동작합니다)
- `/agent` — 병렬 에이전트를 굴릴 때 활성 스레드 전환
- `/theme` · `/apps` · `/status` — 테마, ChatGPT 앱 사용, 현재 세션 상태 확인

> 💡 **하나의 일관된 작업 단위 = 하나의 대화.** 같은 문제의 연장이라면 **같은 대화에 남는 편이 낫습니다** — 추론의 흐름이 보존되기 때문입니다. **정말로 갈라질 때만** fork 하세요.

메인 스레드에서 떼어낼 수 있는 일(탐색, 테스트, 분류)은 **서브에이전트**에 넘기고 메인 에이전트는 핵심 문제에 집중시킵니다.

## 10. 흔한 실수

- **지속적인 규칙을 프롬프트에 욱여넣기** — `AGENTS.md`나 스킬로 옮겨야 할 것들
- **에이전트가 자기 작업을 확인하지 못하게 두기** — 빌드·테스트 명령을 어떻게 돌리는지 알려주지 않는 것
- **여러 단계의 복잡한 작업에서 계획을 건너뛰기**
- **작업 흐름을 이해하기도 전에 컴퓨터 전체 권한을 주기**
- **Git worktree 없이 같은 파일에서 여러 작업을 동시에 돌리기**
- **수동으로도 아직 안정적이지 않은 작업을 예약 실행에 올리기**
